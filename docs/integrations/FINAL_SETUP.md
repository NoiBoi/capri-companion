# Final setup: Capri 0.6.0, Windows and iPhone

This is the consolidated setup guide for Stages 1, 2 and 3. **Your email setup is Outlook only. Skip section 7 (Gmail); it is an optional adapter and stays disconnected.** **Every integration is optional.** Ordinary chat, native memory, affection and movement work with every external source disconnected. Missing credentials are a waiting state, not a reason for another feature to stop.

## Minimum viable setup

1. Start Capri and verify the existing dialogue provider under Model. Keep Memory and local desktop context enabled for sourced understanding. No external integration login is required for ordinary chat.
2. Add one specific local project folder in Connections. Give the project distinctive aliases, such as its repository name and course/project name.
3. Optionally install/pair the Chrome extension and allow only a few sites you want Capri to understand. This plus explicit conversations gives useful project continuity with no cloud OAuth or phone setup.
4. Leave all other source switches off until you choose to follow their optional sections below. Outlook (section 8), then Teams using the same Entra registration (section 9), are the next account steps. Google Calendar is optional even though you use Outlook for mail; phone location and Discord bot access are advanced optional steps.

## Controls and scope

- **Collect observations** permits collection. **Use in live dialogue** permits direct conversation context. **Use in proactive remarks** is a separate permission. A source cannot force a line: existing BehaviorCore, quiet/focus/sleep controls and request budgets still apply.
- **Retain source history locally** plus global saved-history permission enables bounded restart persistence. Choose 1-30 days. Otherwise evidence/checkpoints are session-only. Setup text/configuration and encrypted credentials persist independently from source history.
- **Allow bounded content access** is separate from metadata. Email bodies additionally require selected message IDs and explicit read-body OAuth consent. Teams and Discord content is limited to explicitly selected conversations/channels. No attachments, trackers, images, entire inbox exports or email write operations are implemented.
- **Learn summarized observations in Honcho** requires explicit opt-in, retention and the existing global Memory, automatic learning, saved-history and local Honcho switches. Communication learning exports aggregate counts and explicit project associations, not messages, addresses, grades or private conversations. Discord source learning is unavailable.
- All source content is untrusted evidence, never an instruction authorizing computer actions. Email claims do not prove completion; scheduled meetings do not prove attendance; phone proximity does not prove an activity; opening Gradescope does not prove submission.
- States are literal: disconnected, paused, waiting, syncing, healthy, degraded/error or unsupported capability. A stored refresh credential is **not** proof of current account/tenant access. A localhost receiver is **not** proof of phone connectivity.
- Chrome/project setup drafts autosave. New communication and phone forms need their Save buttons. Save account setup before Authorize, then separately enable/save source controls. Refresh diagnostics after asynchronous authorization/synchronization.

## Chrome

1. Start Capri 0.6.0. Open its panel and choose **Connections**. Keep **Memory** enabled and **local desktop context** enabled in existing settings.
2. In Chrome, open `chrome://extensions`, turn on **Developer mode**, click **Load unpacked**, and select the complete `resources/extensions/chrome` folder. Keep the unpacked folder in a stable location. Chrome may display its normal unpacked-extension notice after restart.
3. Copy the extension's 32-letter ID from its Chrome extension card (also displayed in the extension popup).
4. In Capri **Connections**, paste that ID and click **Generate new pairing token**. Copy the generated token. In the Chrome extension popup paste it under **Pairing token from Capri Connections** and click **Save pairing**. Treat the token as private. Rotation invalidates the previous token. Windows OS encryption stores Capri's token; Chrome stores its copy in extension-local storage. If OS encryption is unavailable, pair again after Capri restarts.
5. In the Chrome source card in Capri, enable **Collect observations** and **Use in live dialogue**. Add exact site origins, one per line, for example `https://github.com` and `https://developer.chrome.com`. No URL paths, wildcard hosts, query strings or trailing slashes. Click **Save source controls**. This starts the authenticated local listener. Pairing alone does not enable collection.
6. Visit an allowed website, open the extension popup and click **Allow this site**. Accept Chrome's permission for that exact site. Both Chrome's permission and Capri's allowlist are required. You can then click **Share headings now**, or wait for a navigation/focus/content update.
7. For selected text or an article excerpt, separately enable **Allow bounded content access** in Capri and save. Select ordinary visible text outside forms, then use **Share selected text once**, or explicitly choose **Share article excerpt once**. Normal passive updates still share metadata/headings only. No full body is sent automatically. Source evidence used in dialogue is sent to whichever dialogue model you configured, with bounded context.
8. In Connections, click **Refresh diagnostics** to see accepted evidence, current projections, source health and candidates. A fresh page is current for at most 90 seconds without another focused sample. Leaving Chrome/focus invalidates it sooner when the bridge is available.

The extension reconnects automatically on future events and its 30-second freshness alarm after Capri restarts; failure backoff caps at five minutes. **Share headings now** retries immediately. It survives MV3 service-worker suspension through Chrome storage. No native messaging registry registration, open firewall port or login is necessary.

If disconnected: verify Capri is running, the source collection switch is on, the bridge says listening, the extension ID matches, both allowlists contain the exact origin, and the paired token is current. A port-in-use message means another process owns `127.0.0.1:43129`; close the other Capri/test instance, then pause/resume Chrome in Connections. Never open this listener beyond loopback. Sensitive URLs, login/payment fields, private browsing, unsupported schemes and inactive windows are intentionally excluded. A blocked page may simply expire without a new record.

**Stop sharing this site** in the extension removes its Chrome host grant and local extension allowlist entry. Also remove the origin in Capri and save to erase that source's contextual evidence immediately even if the extension cannot deliver its removal. **Pause** stops collection and invalidates current source records. **Disconnect and forget** disables permissions, erases contextual source records/aliases/candidates and deletes Capri's pairing secret; to reconnect generate a new token. Remove/uninstall the Chrome extension separately if desired. Source-informed saved Chat stays visible but is excluded from automatic recall and learning.

## Local projects

1. In **Connections**, click **Add project folder**, then select a specific project/repository folder in the native folder picker. Drive roots and user/system profile roots are rejected. Do not select your entire Documents or home tree.
2. Collection and live context start with metadata only, without retained source history or file-content permission. Verify the selected path and healthy watcher status. No opening events are fabricated for every pre-existing file.
3. In **Project identities and associations**, edit **Explicit aliases**, one per line. Add distinctive names, repository URLs and relevant documentation paths/origins to associate browser pages with that project. Click **Save explicit aliases**. IDs remain canonical when a display name changes. Avoid broad aliases like “docs”.
4. File edits and Git branch/HEAD changes now create bounded source events. Watch **Current understanding** and **Recent accepted events**. A filename or commit is evidence of activity, never successful completion.
5. Optionally enable **Retain source history locally** and set **Retention days** (1 to 30). Saved-history privacy must also be enabled. Otherwise observations and candidate consumption are session-only. Optional file content requires **Allow bounded content access**; only supported changed text/source files are read in small excerpts. Dependencies, builds, obvious credentials, large/generated files and symbolic links are ignored.
6. Use **Pause**, **Disconnect and forget**, or **Remove folder** for that project. To monitor a moved folder, remove its old source and select the new path. There is no whole-filesystem or editor-wide permission.


## 3. Google Cloud and Calendar

1. Sign into [Google Cloud Console](https://console.cloud.google.com/), create or select your own project, and enable **Google Calendar API** under **APIs & Services > Library**.
2. Open **Google Auth Platform**. Configure Branding, Audience and Data Access. For a personal external app, add your Google account as a test user while testing. Organization restrictions may require administrator approval. Do not choose a service account.
3. Add exactly these read-only scopes:
   - `https://www.googleapis.com/auth/calendar.events.readonly`
   - `https://www.googleapis.com/auth/calendar.calendarlist.readonly`
4. Under **Clients**, create an OAuth client with application type **Desktop app**. Copy your own client ID and, if supplied, client secret. A desktop client secret is not proof of application identity; Capri also uses PKCE, random state and a temporary localhost callback. Do not configure a web client or an out-of-band redirect.
5. In Capri **Connections > Calendar, listening history and phone location**, save **Google Desktop client ID** and **Google Desktop client secret** using their individual Save buttons. They use Windows credential encryption. If encryption is unavailable, credentials remain session-only.
6. Click **Authorize Google**. Complete the consent in your normal browser within three minutes, granting the two read-only permissions. The browser should show “Calendar authorized.” Return to Capri. No successful authorization is claimed until this actually completes.
7. Click **Load calendars**, select the calendars you want, then **Save integration setup**. Selected IDs remain visible even if the list needs loading again.
8. On the **Google Calendar** source card, enable collection and live dialogue, optionally retention, then **Save source controls**. Click **Sync Calendar now**, then **Refresh diagnostics**. Successful API access shows **healthy**, a sync time and real schedule evidence. **Waiting** means setup is incomplete. **Error** gives the failed step. Retained sync checkpoints require retained history and global saved-history permission.
9. Test with an event on a selected calendar: sync, change its time in Google Calendar, sync after the five-minute polling interval, then cancel it and sync again. The revision should change; a cancelled record becomes a tombstone and disappears from Current understanding. Capri never edits Calendar. Future and recent events are plans, not evidence you attended or completed anything.
10. To revoke, use **Disconnect and forget** in Capri and remove the app from [Google account connections](https://myaccount.google.com/connections). Capri deletes the refresh credential and source evidence; the saved desktop client configuration can be reused. Google-side revocation is only detectable on the next API request. Authorization failures clear old context and require reauthorization. Quota/network failures back off.

Read the [Google desktop OAuth instructions](https://developers.google.com/identity/protocols/oauth2/native-app) and [Calendar incremental sync guide](https://developers.google.com/workspace/calendar/api/guides/sync). Google may impose consent-screen testing/token restrictions; follow the actual console notices for your project.

## 4. Last.fm and Spotify Scrobbling

1. Create/sign into your own [Last.fm account](https://www.last.fm/join). Register an API application at [Create API account](https://www.last.fm/api/account/create). Use your own application details. Capri reads public listening metadata; it does not need an API shared secret, Last.fm password or authenticated scrobble-writing session.
2. Save the issued **Last.fm API key** in Capri Connections. Enter the selected **Last.fm username**, then **Save integration setup**.
3. On the **Last.fm** source card enable collection and live dialogue, and optionally local retention. Save source controls. Click **Sync Last.fm now**, then refresh diagnostics. Recent completed tracks, current scrobbling metadata when available, aggregate familiarity and sync health should appear. No history is invented for an empty/private/unavailable account.
4. To connect Spotify across devices, sign into Last.fm and open [Settings > Applications](https://www.last.fm/settings/applications). Find **Spotify Scrobbling**, click **Connect**, and authorize the intended Spotify account. **Spotify Playback** is a separate feature and is not a substitute for Spotify Scrobbling. See Last.fm's [Spotify instructions](https://www.last.fm/about/trackmymusic#spotify).
5. Play a full eligible track in Spotify, then check the Last.fm profile's recent tracks. A current “Scrobbling now” entry may appear before the completed scrobble. After Last.fm records it, wait at least two minutes and sync Capri. Verify the same artist/title/time. Scrobbling eligibility and delivery depend on Last.fm/Spotify. Capri cannot verify the Spotify connection through the history API, and its status explicitly says so.
6. To change accounts, change the username and save integration setup. This immediately removes prior account context, cached history, candidates and its learned reading. **Disconnect and forget** also deletes Capri's API key. Disconnect Spotify separately in Last.fm if desired.

The adapter uses supported [user.getRecentTracks](https://www.last.fm/api/show/user.getRecentTracks), user.getTopArtists and user.getTopTracks. Recent reads run every two minutes, lifetime favorites at most daily. A bounded historical page is retrieved per pass. Samples hold at most 3,000 completed scrobbles within the source retention window; backfill is gradual and may be incomplete for large histories. Repeated plays at different times remain distinct. Last.fm reports do not create song-change initiatives or model requests. Existing Windows Spotify playback takes priority, with history adding familiarity to that same response. User tastes do not overwrite Capri's opinions.

## 5. Tailscale on Windows and iPhone

1. Install [Tailscale for Windows](https://tailscale.com/download/windows) and the official Tailscale iPhone app. Sign both into the same private tailnet and approve the devices if your tailnet requires it. Keep the iPhone's Tailscale VPN connected when sending reports. Configure tailnet access rules to permit only your intended devices/users to reach this Windows machine's Serve HTTPS endpoint.
2. In Capri, configure OwnTracks as below and enable its source. Confirm the receiver says **Listening on 127.0.0.1:43130/pub**. This status only proves the local listener exists.
3. In Windows PowerShell, inspect existing Serve/Funnel configuration first:

   ```powershell
   tailscale status
   tailscale serve status
   tailscale funnel status
   ```

4. Expose the listener privately with Serve. This command configures HTTPS port 443 and may need adaptation if you already use that Serve port. Preserve existing routes rather than resetting them:

   ```powershell
   tailscale serve --bg --https=443 http://127.0.0.1:43130
   tailscale serve status
   ```

   Follow Tailscale's HTTPS enablement instructions if prompted. Copy the actual HTTPS hostname printed by Serve; append `/pub`. Do not invent a hostname. **Do not run `tailscale funnel` to expose this receiver.** Verify Funnel is not enabled for this port. Capri cannot prove your tailnet ACLs or Serve/Funnel configuration from a localhost listener.
5. Keep the Windows PC awake, Capri running, and Tailscale connected for timely reports. Serve may persist after restart, but Capri's receiver only exists while Capri and collection are running. To remove only this Serve listener when finished:

   ```powershell
   tailscale serve --https=443 off
   ```

See [Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve). Serve is private to the tailnet; Funnel is public and must not be used here.

## 6. OwnTracks for iPhone

1. Install the official [OwnTracks iOS app](https://owntracks.org/booklet/features/ios/). Grant location access **Always** and enable **Precise Location** in iOS Settings for OwnTracks. Enable Background App Refresh where available. Contacts, microphone and photo access are unnecessary for Capri's receiver.
2. In Capri Connections, enter a device name such as a name you choose for this phone. Use only letters, digits, underscore or hyphen. Click **Generate OwnTracks credential**. Copy the generated username and password from the `username:password` field now. The password appears only at generation and is saved using OS encryption. Rotation invalidates the previous credential.
3. Click **Add named place**. Enter your chosen place name, latitude, longitude and radius in metres, then optionally select associated projects. Use 50 to 5,000 metres; 150 to 300 metres can reduce boundary drift where appropriate. Save integration setup. Coordinates are local configuration, never prompt evidence or Honcho input. Remove a place and save to invalidate prior location context and learning.
4. In OwnTracks connection settings choose **HTTP** mode, URL equal to the actual Tailscale Serve HTTPS URL ending in `/pub`, and configure Identification with the generated username, generated password and the **exact device name saved in Capri**. Set a two-character tracker ID if requested. Basic authentication must be enabled. Use HTTPS; do not disable certificate checks. Do not enable OwnTracks payload encryption: this receiver accepts authenticated HTTPS JSON rather than OwnTracks encrypted envelopes.
5. If your OwnTracks version offers regions/geofences, create geographical regions with names, coordinates and radii matching Capri's places. Region transition reports are accepted only when their reported coordinates/accuracy independently support the configured named place. Unknown regions, beacon-only transitions or missing coordinates/accuracy cannot establish proximity. Capri also derives visits from ordinary valid location fixes, so matching iPhone regions help reporting but are not a requirement for every arrival.
6. On Capri's **OwnTracks** source card enable collection and live dialogue. Optionally enable retention and choose 1 to 30 days. Save source controls. Use OwnTracks' manual publish/send-location action. Refresh diagnostics in Capri. Only an authenticated report from the selected device with valid timestamp, coordinates and accuracy yields a successful sync time and place evidence.
7. To diagnose, inspect OwnTracks' connection/error status. An authentication failure means regenerate/re-enter the credential. HTTP 422 means an unsupported payload, wrong device, future timestamp or malformed coordinates/accuracy. Known non-location metadata is acknowledged without ingestion. Valid reports outside retention or with accuracy worse than 200 metres are acknowledged and ignored so a queued old fix cannot block recovery. A connection error may mean the PC is asleep, Capri stopped, Tailscale disconnected, tailnet access blocked, or the Serve URL incorrect. Never open the receiver to the LAN or public Internet as a workaround. The JSON reply for an accepted location is `[]`.
8. Test a real arrival/departure from a named place. Accuracy-aware boundaries deliberately avoid toggling in GPS uncertainty. Dwell requires reports supporting at least ten minutes near a place, with no observation gap over ten minutes. A phone visit is not proof of class attendance, a workout, a lab experiment or the user's physical presence.
9. **Pause** on OwnTracks immediately stops the listener and invalidates its evidence/learned reading. **Disconnect and forget** deletes contextual location history, receiver credential and learned reading while preserving named-place setup. Re-enable only after generating a new credential. Global **Disconnect all and clear Life Context** applies to all sources; it does not delete ordinary saved Chat or approved memories. Remove named places separately if you also want their local coordinates deleted.

OwnTracks can queue reports while disconnected; [HTTP delivery behavior](https://owntracks.org/booklet/tech/http/) and [payload timestamps](https://owntracks.org/booklet/tech/json/) are authoritative. Reports more than five minutes old are historical and cannot create a return greeting. Out-of-order reports do not rewind the latest place state. Reports beyond retention or with accuracy worse than 200 metres are ignored; future timestamps beyond one minute are rejected. Authenticated traffic is limited to 120 requests per minute. No continuous tracking is promised.

Changing OAuth scope/client configuration invalidates old source context and requires new consent.

Also revoke the application in your Google Account Connections when desired. Provider-side revocation is detected on the next API request. ## 10. Gradescope and academic alternatives

Direct automated student account access is **unsupported in this release**: a supported public student API was not established in the official documentation reviewed. Capri does not use community private endpoints, passwords, MFA workarounds or unattended Gradescope scraping. [Gradescope help](https://www.gradescope.com/help) documents course/student workflows and institutional/manual integrations; those do not establish a public personal student API.

Choose legitimate alternatives independently:

1. **Notification emails:** Select the folder/label receiving your Gradescope notices in a permitted Gmail/Outlook source. Gradescope sender-domain claims plus subject text distinguish assignment, deadline, submission and grading notices. They remain email claims; they do not constitute direct Gradescope verification. Selected bodies can supply bounded explicit information when separately authorized. A display name alone is not trusted as the sender domain.
2. **Calendar:** Use events already legitimately present in a selected calendar. A schedule/deadline is not a submission or completed assignment.
3. **Open-page Chrome semantics:** Explicitly allow the actual Gradescope site origin in both the extension and app. Only an already-open focused page is observed under the existing Chrome boundaries. Use a deliberate selected-text share for appropriate details. Login/MFA/forms remain excluded. Opening an assignment does not prove submission, grading or completion.
4. **Manual records:** Enable Academic imports collection in Connections. Expand Gradescope alternatives and academic records. Enter course, assignment, a distinct state (assigned, due, submitted, graded, feedback, cancelled), optional due time, and the evidence note. Due times must be ISO 8601 with an offset, for example the format `YYYY-MM-DDTHH:MM:SS-04:00`; use the actual official deadline and correct daylight-saving offset. Add academic record. Repeating a course/assignment updates its stable manual record. Evidence text is kept only with content permission. Live/proactive use remains separately controlled.
5. **Manual JSON:** Import academic JSON file accepts at most 200 validated records / 256KB. This is a normalized user-supplied file, not a claim of an official Gradescope export format. Each record needs `id`, `course`, `assignment`, `status`, `at` (actual observation/report time with timezone), `evidence`, optional `due`, and optional `entities` containing existing explicit association IDs. Use your own exported/authorized information. Do not backdate a fresh observation to a semester-old creation time; retention and stale-event rules apply. Unsupported fields/formats are rejected rather than guessed. No PDF/gradebook scraping occurs.
6. Verify the exact evidence type/source. Submitted and graded are distinct from completed; no state is automatically upgraded to completion. Updated deadlines can support a question/callback after stronger context, without inventing progress. Numeric grades and full feedback do not automatically enter Honcho.

## 11. Discord, optional

A bounded Windows tasklist query once a minute checks the standard Discord.exe process; actual existing foreground observations distinguish Discord foreground from merely running. 3. Test by foregrounding Discord or a configured game. A process observation is not account authorization. Local activity creates no model request by itself and has no Honcho learning.

### Selected guild channels and optional guild voice membership

1. Create an application and bot in the [Discord Developer Portal](https://discord.com/developers/applications). Keep the bot token private. In Capri save **Discord bot token**. User tokens, self-bots, Discord client injection and account scraping are unsupported and rejected. The API identity must actually be a bot.
2. With the server owner's authorization, invite the bot using OAuth2 URL Generator with scope `bot` and only **View Channels** and **Read Message History**. The permission value is 66560. For optional selected-guild voice membership add **Connect** (combined value 1115136); the bot does not join a call or capture audio. An example invite template is `https://discord.com/oauth2/authorize?client_id=<YOUR_APPLICATION_ID>&scope=bot&permissions=66560`. Replace the placeholder with your own real app ID. Do not grant Administrator or Send Messages.
3. For bounded message content, enable the **Message Content Intent** in the bot settings, complete any Discord-required approval, and separately enable bounded content access on Capri's Discord authorized bot source. Without it, content may be empty; Capri does not fabricate text or claim full message access. Metadata-only is the default.
4. Use Discord Developer Mode > Copy Channel ID for each permitted guild text channel/thread. Enter those IDs in Authorized Discord channel IDs, one per line, and save. Bot DMs, categories, voice-channel text and unselected channels are excluded. Verify the bot has access to the selected channels, not merely server membership. Excluded author IDs can be entered independently.
5. Optional voice connection metadata: enter one real guild ID and your own real Discord user ID in Optional voice guild/user ID. The supported official Get User Voice State endpoint reports connection membership in that authorized guild if the bot has permission to connect to the relevant channel. It does not detect speaking, private/DM calls or account-wide voice status. Do not infer the selected identity is you without configuring it deliberately.
6. Enable Discord authorized bot collection, optionally live/proactive use and content, save controls, then Sync. Polling is bounded to one-minute intervals. Recent windows catch edits, checkpointed after-pages catch new messages, and five older retained message IDs per pass are audited for deletion. Absence from a limited recent list alone is not deletion proof. Permission loss clears stale source context. API throttling backs off.
7. Verify a real permitted channel message/update or a voice membership change after setup. Fixtures do not establish server access, privileged intent approval or voice permissions. Third-party messages and Discord activity never automatically enter Honcho/permanent personal memory. Disconnect and forget deletes Capri's bot credential and contextual records; remove the bot from the server separately if desired.

Sources: [Discord messages](https://docs.discord.com/developers/resources/message), [voice state access](https://docs.discord.com/developers/resources/voice), [rate limits](https://docs.discord.com/developers/topics/rate-limits).

## 12. Associations, Honcho and retention

1. Existing project identities/aliases associate local folders, browser metadata, meetings and communication titles. Use Add an explicit association for a person, project, course or commitment, with distinctive names/addresses/identifiers. These are user-confirmed associations, never fuzzy model-created identities. Named places can be associated with those identities. A common entity near observed/planned times supports a qualified cross-source connection, not causation or attendance.
2. Fresh context is selected fairly across sources; busy mail cannot fill every slot. A relevant explicit project query can retrieve up to two dated retained historical records. Tombstones, pauses and revocation exclude obsolete data. A historical report is never current whereabouts or completed work.
3. Native PersonalContext commitments remain based on explicit user statements; messages requesting work do not silently become a personal promise or completion. Native relationship/taste memories remain independent from listening history and third-party preferences.
4. Only opt-in eligible sources have summarized learning. Calendar/Last.fm/OwnTracks use their existing summary rules. Gmail/Outlook/Teams/manual academic learning exports bounded aggregate type counts and explicit project names, not subject/body text, addresses, grades or feedback. Discord and Chrome/project source learning are unavailable. Source-informed assistant dialogue is visible in Chat but excluded from automatic native/Honcho recall and learning.
5. Existing local Honcho must be installed/enabled in Memory. The previous live check reported its local adapter allowance exhausted at 64/64; no reset or bypass is part of this upgrade. Real derivation needs an available legitimate service allowance. Check the configured Honcho status/launcher, but do not confuse import success or HTTP health with completed derivation.
6. Each source's learned reading is independently erasable using the existing Honcho erasure queue. Source changes, exclusions, revocation and entity changes immediately block affected cached interpretations. Honcho HTTP 202 is acceptance, not completed deletion: a durable tombstone remains through restart until the workspace actually disappears. Pending deletion is reported honestly and old recall remains blocked. No user data is deleted to make tests pass.
7. Direct/proactive controls also filter source-tagged shared assistant turns. Mixed cached BehaviorCore interpretations are conservatively withheld from a mode that disallows a source; native approved memories, physical body state and allowed direct interaction remain. Separate explicit Chrome/screenshot grants are independent permissions and should be configured accordingly.

## 13. Verification, troubleshooting and honest states

1. Before any account setup, verify ordinary chat and movement and that all unconfigured sources say disconnected/waiting. Existing configured Stage 1 sources may remain enabled; the upgrade does not reset them.
2. After each setup, Save its form and source controls, Sync where applicable and Refresh diagnostics. Check real source timestamps, recent accepted events, current direct/proactive interpretation, candidates and last successful synchronization. Initial account backlog stays quiet. Manual Sync respects polling/backoff deadlines and is not a quota bypass.
3. Test Calendar reschedule/cancel; a Gmail/Outlook notification and selected Teams message with a shared explicit project; a new approved local file/Git change; repeat Last.fm scrobbles; a real OwnTracks visit; academic status changes; Discord local foreground and any authorized bot signals. No test needs to fabricate completion. Silence is valid.
4. Authorization failures: check client type, exact callback, tenant/account type, enabled APIs/scopes, test-user eligibility and actual administrator consent. Microsoft's callback is exactly `http://localhost:43131/oauth2callback`; Google Desktop callbacks use a generated loopback port. Do not extract client tokens or bypass university policy. Complete one communication OAuth flow at a time. Credentials use OS encryption; when unavailable they are session-only.
5. API/network failures: check service availability, selections and provider quota. Narrow large Gmail labels/Outlook folders/Teams conversation lists. Expired Gmail history or Outlook delta checkpoints trigger a bounded rescan; never delete your profile. Backoff caps at an hour. OAuth revocation clears dependent context and needs explicit authorization again.
6. Location failures: inspect OwnTracks/Tailscale connection status, actual device name, HTTPS certificate, private access rules, generated Basic credential and receiver status. The PC must be awake and Capri running. Queued old reports cannot create present-tense greetings. Never switch to public Funnel or open the listener to the LAN to work around a failure.
7. Retention/exclusions: Pause invalidates source context and stops collection. Disconnect and forget erases source evidence/checkpoints/candidates, its credential and learned reading. Exclude this record removes its source context and prevents re-ingestion while excluded. Mail exclusions can be edited under account setup; source-wide forgetting is always available. Explicitly remove named places to delete their setup coordinates. Saved Chat is a separate user-visible transcript; source-derived Chat does not become automatic recall.
8. Use the installed STATUS.md/report for the actual deterministic, packaged, real-service, awaiting-authorization and unsupported results. Synthetic successful responses never establish real account access. First real-model samples, including weak/error/silent outputs, are retained.

## 14. Installation and rollback

The installer is Capri-Setup-0.6.0.exe. The established build runs typecheck/unit tests, build, focused Electron checks, dist, then isolated packaged checks. Account/phone configuration is not required to install or run it. Extension resources, Koffi and integration documentation are included.

The stopped portable app and full profile are backed up before replacement. The final report gives the exact rollback and profile-backup paths. To roll back: stop Capri, archive the current app/profile without deleting newer data, restore the old portable directory, and restore the corresponding stopped-profile backup if the old version cannot read new permission fields. A package-only rollback to older strict schemas may fail; do not delete source data to force a launch. Keep the new profile separately before restoring an older backup. Native memories, credentials, preferences and history are preserved and checked during deployment.
